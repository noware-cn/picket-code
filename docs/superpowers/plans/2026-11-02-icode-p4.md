## Review Focus

1. **恢复一个 iCode 侧已经删掉的会话**：`session/load` 会返回 `Session not found`。此时面板必须仍然打开（空历史），下一轮自动 `session/new`，而不是抛错把聊天卡死。
2. **恢复回放期间用户点了取消/关掉聊天**：回放是几十条通知，中途 `abort`/`disposeChat` 不能留下悬挂的回放缓冲或把迟到通知写进实时映射。
3. **`ask_user` 的三种答复**：accepted（带多选/自由文本）、declined、cancelled，以及 iCode 侧「答案数量必须等于问题数量、自由文本放 `values` 而不是 `note`」的严格校验——数量不匹配会被当成「没有回答」。
4. **同一 chat 并发**：既有单 turn 守卫必须继续生效，恢复后第一次 `sendMessage` 不能再发一次 `session/new`（否则历史分叉）。
5. **`_chrys/turn_started` 每轮重试都会重发**（同 `turnId`、`isRetry:true`）：activity 文案不能被重试重置成「准备中」，也不能在首个 token 到达后残留。

## 明确不做（以及原因）

- **`FileEditTracker` 路线（原方案 B）**：类在 `node/shared/fileEditTracker.ts:33`，需要 provider 在每次编辑前后各做一次快照并 `takeCompletedEdit(...)`。iCode 的编辑发生在 ACP 子进程里，我们只能靠 `tool_call`/`tool_call_update` 两侧自建 before/after 存储——git 路线（Task 5）已经给出更准的 blob diff，这条只作为「需要 `file_edits` 的其他下游（编辑存活统计、归属）」时的独立 spike。
- **工具级 `FileEdit` 内容（路线 C）**：`ChatToolCallComplete` 附 `ToolResultContentType.FileEdit` 能让每次工具调用都列文件（`agentSideEffects.ts:1095-1100` 还会触发重算），但缺 before 字节时 UI 只能把文件跟自已比（`agentHostResponseFileChanges.ts:533-538`），做不出真 diff。留作非 git 目录下的可选增强。
- **`session/list` 对齐**：iCode 有 `session/list`，但宿主只通过自己的 catalog 列出会话，接进来需要 host 改动，收益低。
- **多轮增量上下文复用**：iCode 会话本身有历史，恢复后继续用同一 sessionId 即天然增量，无需额外实现。
- **Windows 真机冒烟**：仍只到单测。
